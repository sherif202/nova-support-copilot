Model Selection

Build or buy, which vendor and which model runs each step, what a conversation costs, and the bake-off that decides. The rule is simple: the cheapest model that passes every gate in the eval set wins, whichever vendor makes it.

Phase 2 of 4 · Build Do: Compare models on your eval set: quality, cost, speed. Catch: The biggest model is rarely the right one. Pick the cheapest that passes.

Flow

Only 2 of the 7 steps call a model

Everything that must never go wrong stays in code
1 · codeInput checksEmpty, too long, flood, card numbers masked
2 · modelUnderstandLanguage, intent, priority, confidence as JSON
3 · codeRouteFraud words win; P0 never reaches step 5
4 · codeLookupTop 3 records, live notices
5 · modelAnswerOnly P2 and P4, from policies and records
6 · codeOutput checksIDs exist, numbers match, blocked words
7 · codeClose or moveTicket, masked log

The judge (step 3 of the eval framework) runs offline on the eval set, never on a live chat. Because fraud is routed in code, fraud recall doesn't depend on which model we pick. The model only has to be good at understanding and wording.

No vendor publishes a Franco-Arabic banking test. Nile-Chat (MBZUAI) beats Llama, Jais and ALLaM on Egyptian benchmarks in both scripts, but it's a small research model. Only our 60 cases, written in the way Nova's customers type, can tell the vendors apart.

So we start on the cheap tier, and the target is set per message: EGP 0.035. Per conversation, the pilot may reach EGP 0.20, and must be at 0.10 by week 8. Fallbacks

When the model fails

What happensWhat the copilot does
Timeout or errorRetries once, then shows the safe message and hands off to a person
Model declines (refusal)Hands off to a person. Haiku has no automatic fallback. If Sonnet is chosen, turn on the API's built-in fallback
Broken JSON from step 2Treated as low confidence: offers a person, never guesses
Answer fails an output check (unknown ID, wrong number, blocked word)Rewrites once, naming the failed check. If it fails again, hands off to a person. Never a third try
Primary vendor down or slow twiceThat message goes to the backup vendor, once
Anthropic down, or something looks wrongKill switch COPILOT_ENABLED=false: every message goes to a person
A model is retiredChange the ID in .env, rerun the bake-off and eval, and ship only on a pass
Baseline

Pin it so every change is comparable

  • Model IDs and effort live in .env, never hard-coded
  • Save the winning run as logs/baseline.json, with the models, effort, a hash of the system prompt, the eval set version and every score
  • Every later change runs as a candidate against that baseline (step 7 of the eval framework)
  • Don't send temperature: the current API rejects it. Use effort to trade quality against cost
  • Step 2 uses structured JSON output, so the reply always fits the schema
Learning

Where Nova's learning lives, so a new model starts where the old one stopped

Kit: knowledge/examples.jsonl and docs/06-LEARNING-LOOP.md

Nova doesn't train the model. Everything learned from real customers goes into plain files Nova owns, and every model reads the same files on every message. Nothing is stored inside a model, so nothing is lost when we switch.

The weekly loop

1 · Real messagePilot customers writeMasked before it's saved
2 · Find the misreadSignalsAgent correction, retry, handoff after a wrong answer, low confidence
3 · Fix the knowledgeNot the modelAdd a trap, an example or a policy line
4 · Lock it inAdd an eval caseSo the fix can't quietly break later
5 · Prove itRerun the evalShip only if it beats baseline.json
↺ every week, so each misread happens once

Teal edge: read by the model on every message, cached, so each costs almost nothing. The rest are written by the app or by people, and the model never reads them directly. Never copy an eval or hold-out case into examples.jsonl, or the test stops meaning anything. The kit's checks enforce this.
