Order matters. Everything that is the same for every message comes first, and the per-message part comes last. Cached input costs about a tenth of normal input, so the long part costs almost nothing after the first message. One changed character above the cache point and every message pays full price.

Check it, don't assume it. Each vendor caches only above a minimum size. If the log shows zero cached tokens, the prompt is under that vendor's minimum and the cost per message is higher than the Stage 3 table. The fix is cheap: add the next approved examples. The first real run on 30 Oct showed it working: the first message wrote 7,117 tokens to the cache, and every message after read them back, adding only 17 to 30 new input tokens. That is about double the first estimate, because Arabic text uses more tokens than English. The split inside the bar is estimated; the total is measured.

Do

Every failure becomes an example

Section 7, "bad, then fixed"
Minimum fee
Bad"The fee is 3% of 1,500, so 45."
Fixed"3% with a minimum of EGP 75, so 75 (FEE-2.4)."
A price that isn't there
Bad"A safe deposit box costs EGP 500 a year."
Fixed"I don't have that price. A colleague can help."
A promise
Bad"Your dispute is approved and the money will be refunded."
Fixed"It's under review. Only the Disputes team decides (DSP-5)."

Never paste a test case. Each example teaches the same lesson as a failing eval case with different words, amounts and dates. If the model has seen the test, the test proves nothing. While writing these, the check found two eval messages (cases 10 and 11) copied word for word into the taxonomy's traps table. They are reworded now, with the same meaning, so those two cases are a fair test again. The kit's validator now blocks this for every prompt and knowledge file.

Catch

Version it like code

prompts/CHANGELOG.md
1 · PickThe worst failureFrom step 14, fraud and harm first
2 · Change one thingA rule, an example or a trapIn a file, never in the code
3 · BumpThe versionPatch: wording · minor: a rule · major: the JSON shape
4 · RunAll 60 casesSame model, same eval set
5 · RecordScores in the changelogA hard-gate failure is never shipped

Stop when it converges: two versions in a row within 0.02 of each other with no hard-gate failure. More tweaking after that is tuning to the test. Then open the sealed hold-out, once.

Every turn is traceable. The log stores the prompt version and a short hash of each filled prompt, next to the model and its cost. baseline.json stores the version that passed, so a later model or prompt must beat it.

Stage 3 link

One set of prompts for every vendor

  • Plain Markdown headings and simple tags like <policies>, which Claude, GPT and Gemini all read the same way.
  • Output is one JSON object. The adapter also switches on each vendor's structured-output mode, and code checks the JSON anyway.
  • No temperature, no "think step by step", no tricks only one vendor understands. The steps are written out instead.

If one vendor needs a different prompt, that's a bake-off finding, not a second prompt. Two prompt sets would double the testing and break the promise that switching vendors keeps everything learned. Model, prompt version and score move together in baseline.json.
