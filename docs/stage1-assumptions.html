What has to be true for the copilot to work

The copilot is built and passes its own tests (version 1.0.13), but every number so far comes from synthetic data. This page lists the assumptions underneath it: what each one decides, what the build has and hasn't shown, the real data that would test it, and the result that would break it. It's written to agree, with the instructor, which real data to start with.

Prepared by Sherif HilalNova Bank is a fictional bank from the course brief24 assumptions · 6 areas

The five that make or break it

If any of these turns out false, the product changes shape, not just its numbers. Test these first.

A1 · Need

Most in-scope contacts need information, not an action

If customers mostly want something done (block, refund, open a dispute), an answer bot deflects little.

Test: 3 months of contact reasons with resolution codes, plus one agent interview ("of your last 20 calls, how many needed no action?"). Breaks if over half need an action.
B2 · Feasibility

The bank can give read-only access to the customer's records

Every grounded answer depends on this customer's transactions, disputes and cards, in real time.

Test: IT's API inventory for core banking, disputes and the card system. Breaks if there's no read-only access within the project window.
D1 · Regulation

Customer data may be processed by the AI provider

Central Bank outsourcing and data-residency rules decide the vendor, the hosting and the cost.

Test: a written opinion from Compliance. Breaks if no cloud provider is allowed and no in-country option is available.
B1 · Feasibility

The answer is in the records and the rules

The shadow run resolved 23% before the synthetic tickets were linked to the records and 63% after. Real coverage decides the North Star.

Test: 200 real tickets matched to their records and the policy that answers them. Breaks if over 40% have no source.
A3 · Need

Callers will use chat

The brief says the app is used only for balance checks. If callers aren't app users, the channel is wrong.

Test: channel mix, app monthly users, and whether in-scope callers use the app. Breaks if most callers don't; then WhatsApp comes first.

The real data to ask for, in order

Each item tests the assumptions in brackets. All of it can be anonymised: masked customer IDs, no names, card numbers cut to the last 4 digits, under the course's or the bank's confidentiality terms.

  1. Three months of contact reasons, with resolution codes and handle timeTests A1, A2, C1. The cheapest and most decisive item.
  2. One hour with a contact-center agent and a supervisorTests A1, E1. "Of your last 20 calls, how many needed no action?" and how agents are measured.
  3. 500 to 1,000 anonymised customer messages (chat, WhatsApp or call transcripts)Tests A5, B4, B5, F1. Replayed through the existing eval at about US$0.03 per 100.
  4. 200 tickets with the matching (anonymised) transactions, disputes and cardsTests B1, F2. A real shadow run, the same way as the synthetic one.
  5. The real fee schedule, dispute and card policies, with ownersTests B3. Replaces the synthetic handbook, rule by rule.
  6. Channel usage: app monthly users, chat and WhatsApp volumesTests A3. Decides chat versus WhatsApp first.
  7. Card decline codes and hold data from the card switch (a sample)Tests B6. What the investigator can explain.
  8. A Compliance view on AI providers, data residency and log retentionTests D1, D2, D3. Decides the vendor before any real data leaves the bank.
  9. Agent cost, hiring plan and IT running costTests C1, C2, C5. Turns the ROI model's assumptions into the bank's numbers.

Nothing in the build needs rewriting to use real data: the copilot reads its records, policies and test cases from files, so each data set replaces its synthetic version and the same eval, shadow run and ROI model run again.
